## 二、判据（写死判定方式）

### 2.1 工具 A：正确性四项

记录以 `\n\n` 结束，正文不含空行；判据流式切条，不把整卷读进一个字符串。

| 项 | 判定方式 |
|---|---|
| ① 总条数 | 按 `\n\n` 流式切条，完整记录数必须等于 N；空块、尾部残字节均判失败 |
| ② 逐行 sha256 | 由独立规格（`bench/common.py`）预生成清单：每条期望字节的 sha256 + 字节长度。实际每条取 sha256，**按多重集与清单逐项相等**（并发顺序不定，故不按行号对位）；同时逐条长度必须相符 |
| ③ 无交错 | 每条必须是**单个物理行**（记录内不得含 `\n`），且整行匹配结构正则：`[时间] [类] [标题] [作者] [id=m十六位] [sig=六十四位] SEQ=数字 PLAN=十六位`；每条以 `\n\n` 收尾；无空块、无尾残 |
| ④ 无重号乱序 | 以 `SEQ` 为键建 1..N 位图：每条必须命中且仅命中一次，越界即失败。跨写者顺序不作要求（并发追加本就允许交错到达）；同写者序号递增在 B 中另由 V5 检查 |

另加两条旁证：记录长度逐条对清单；抽验若干条用 orch 自己的 `entry_auth` 验签。

### 2.2 工具 A：判据自证（先自证，后上规模）

- 做法：1 万条 × 8 写者。0 号写者把一条记录**拆成两段** `write`（不加锁），先写前半；与 1 号写者握手，1 号在中间**完整写一条**；0 号再写后半。这是真实撕裂的同构字节。
- 预期红：②逐条 sha256、③无交错、长度对账三项红；①总条数仍为 1 万（撕裂改内容不改条数）。
- 实际：三项红，①绿；随后正常写四项全绿。
- 门禁：若注入后仍全绿，`run.sh` 立即中止并打印「判据失效，本次读数作废」，后续档不跑。

### 2.3 工具 B：V1–V6

| 项 | 判定 |
|---|---|
| V1 | 完整记录数 = 期望 |
| V2 | 非空行数 = 完整记录数（抓撕裂/外来行） |
| V3 | (写者, 序号) 全覆盖、无重复、不越界 |
| V4 | 正文校验位 = `md5(写者+序号)[:8]` |
| V5 | 同写者序号严格递增 |
| V6 | 记录头六段齐、作者与正文写者一致 |
| V0 | 整卷合法 UTF-8 |

自证：E2/E4 人为注入、E5 真并发「头/体两次 write」反证、E8 单条篡改。四项均红，且我复跑其 `verify()` 输出与日志逐字一致。**口径差异**：V4 是校验位，不是对预生成清单的逐字节 sha256；能抓单条改写（E8 已证），但对时间戳等非校验字段的系统性改写不敏感。

### 3.3 换算与不可比性（必须一起看）

- **每条字节数差 2.70–2.76 倍**：A 的记录带 `[id=]` 与 64 位 HMAC 签名，B 的只有 8 位校验位。因此「条/秒」不能直接横比，卷大小更不能直接横比。
- **按条速**：10 万档 A/B = 93,257/59,954 = **1.56×**；100 万档 = 62,739/59,753 = **1.05×**。
- **按字节速**：10 万档 18.27/4.25 = **4.30×**；100 万档 12.35/4.35 = **2.84×**。
- **按单条耗时**：10 万档 10.72 µs vs 16.70 µs（1.56×）；100 万档 15.94 µs vs 16.74 µs（1.05×）。
- 解释：100 万档两套的单条成本基本相等（差 5%）；10 万档 A 快 1.56 倍，主要是短跑固定开销占比、Python 3.14 与 3.9 的解释器差异、以及 iMac 为 Intel、A 为 M2。字节速差 2.8–4.3 倍是记录长短叠加所致，**不是同一工作量的快慢**。
- 容量规划建议：以「条/秒」与「B/条」两列一起算磁盘与耗时，不要只看条速。

## 五、已知瓶颈（本机 100 万卷实测）

1. **多级目录生成最重**：17.564 s、写 436.2 MB、峰值 1.48 GB——时间与内存双第一。
2. **digest 整卷读放大**：只取 20 条却读 3.94 GB（≈20 × 全卷），条目/引用越多线性恶化。
3. **超 PIPE_BUF 走加锁路径**：B 实测 632 字节/条时吞吐 60k → 10.3k（**5.82×** 下降），且每条打一行提示；A 的 196 字节/条未覆盖此路径。
4. **64 写者后饱和**：B 实测 1→8→64→256 写者为 13.3k→49.1k→60.0k→59.8k 条/s；256 是竞争不是并行，未塌。
5. 次级成本：`query` 命中即整卷入内存（1 条命中读 196.9 MB、峰值 836 MB）；增量索引便宜（追加 1 万后 0.716 s）。

## 七、结论（只落到证据上）

1. 写卷在 **8 / 64 / 256 并发**下零错：A 四绿、B 绿（V1–V6），且 B 的 100 万卷经我独立整行复算一致。
2. **1000 并发未验证**：两套都没跑。不能判「零错」，也不能判「有错但可解释」。已证上限是 256。
3. 百万级瓶颈在**多级目录生成**与**digest 整卷读**，不在写卷，也不在增量索引。
4. 回包额外证实：超 PIPE_BUF 是性能悬崖（5.82×）；64 写者后饱和。
5. 待办：4.0.4 落地后把本记录与两套工具一并入仓；入仓前不触碰 `daybook-suite`。
